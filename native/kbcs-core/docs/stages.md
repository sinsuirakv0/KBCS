# ステージの出現処理

2026-10-21、JP15.7.2 ARM64。対象SHAと解析の入口は[番台別調査](../../../research/docs/stages/README.md)。現版`006ef2b0`の待機更新・出現行選択・成功後の更新を`src/stage.cpp`へ移植した。原本の読込、戦闘開始、敵個体の生成、ボス演出、報酬は別の処理。

## 関数と状態

`kbcs-bridge::stage::tick` → `kbcs_core_stage_tick`が、行状態と全体状態を更新して候補行を最大1件返す。候補−1は出現なし。`Row`はネイティブ読込後の14整数であり、CSVの生の14セルではない。待機列2/3/4は×2済みで、終端行は渡さない。

`State`はwait / spawned / killsの3整数。`Context`は全体待機、今回の撃破差分、敵の現在数/上限、城HP/最大HP/累積被ダメージ、判定方式、休止、全体生産間隔の両端を持つ。入力バッファは呼出中だけ借用する。C++はポインタやシミュレーションの状態を保持せず、ヒープ・例外・乱数生成器を使わない。

候補行の敵生成を呼出側が試み、成功した場合だけ、全体間隔の乱数→行間隔の乱数の順に引き、`PendingSpawn::commit(self, ...)` → `kbcs_core_stage_commit`へ渡す。通常の乱数値は0以上、両端差以下。0.1.14では逆転区間も受理し、その場合の抽選値は0だけ。生成失敗時は候補を破棄し、間隔乱数を引かない。生成内部のレイヤー抽選は別に消費する。0.1.10から借用した候補を消費し、Rustでの再commit・状態差替えを防ぐ。C ABIの所有契約と初回出現フラグは[監査結果](audit-20261022.md)を参照。

分離する目的は、実際の敵生成が失敗する分岐を再現し、失敗時の間隔乱数消費を避けること。将来のC++バッチ実行も同じ関数を内部から呼べる。Rustから毎フレーム呼ぶことを前提にした描画APIではない。

## 順序

1. 撃破差分を取り出して0へ戻す。休止時もここまでは実行し、待機と候補は更新しない。
2. 全体待機を1減らす。全行を元の順に巡回し、城条件が成立した行の撃破累計へ差分を加える。
3. 撃破条件不足かつwait<2ならwait=1。城条件成立時は有限数を使い切っていなければwaitを減らす。城条件不成立では列12が0の行だけwait=1へ戻す。
4. 全体待機<1かつ敵数<上限なら、後ろから最初のwait<=0を候補にする。
5. 敵生成成功後に限り全体待機・その行の待機を抽選値へ更新し、生産回数を1増やす。

城HP条件は`castle_hp <= row[5] * castle_max_hp / 100`。敵城指定があり、さらに対応する敵原CSV49が非0の経路だけ、`castle_damage >= row[5]`になる。呼出側が確認した結果をdamage_conditionへ渡す。敵城指定の有無だけから設定しない。0番台の敵城指定4面は原敵ID317・CSV49=0である。

## ABI・入力の限界

既存のABI2へ関数と別PODを追加した。旧計算関数のシグネチャ・構造体・ruleset1507021は変更していない。ABI2で追加された入口が利用可能な新版ライブラリと一緒にビルドする。新しいHTTP APIやUIのスケジューラ公開は行っていない。

エラー0/1/2は成功/入力不正/整数境界。行数は0〜4096、現在敵数と上限は0〜50、待機間隔の両端・出現回数・撃破累計は非負。更新前に全入力を検査し、エラー時は候補と状態を部分更新しない。ネイティブで32bit積・加算や乱数範囲があふれる入力は拒否する。極端なオーバーフローの再現は対象外。

## 検証

`research/verify/stages.py --publish`が現版命令の16条件を小さい`tests/stage-vectors.json`へ出力する。`kbcs-bridge/src/stage.rs`の1テストがC++の候補行・全行の3整数・全体待機・撃破差分と比較する。通常城、累積ダメージ型、敵城指定があってもCSVフラグ0の経路、休止、生成失敗、逆順優先、乱数の端を含む。入力エラーによる部分更新も確認する。

敵個体の姿勢・生死・出現可否、敵城の初期化、開始時の間隔抽選、ボス衝撃波、撃破差分の生成元、編成制限・報酬・XP・素材はこのAPIへ含めない。0番台の完全な戦闘を実装したという意味ではない。

## 0番台XP（0.1.7）

`kbcs-bridge::experience::legend`→`kbcs_core_legend_experience`は現版0058bad0のkind0経路を共通化する。入力は原XP B、クリア済み回数c、表示勉強力Lv L、章別に整数化済みのお宝加算T、XPコンボ合計P、おかめ0/1。出力5段階は、F=B×9、A=F−floor(F×min(c,4)/5)、S=floor(A×(100+(L−1)×5+T)/100)、C=floor(S×(100+P)/100)、おかめ時floor(C×15/10)。原値0は0のまま。

お宝は日本編3章の各floor(50×完成率/100)と宇宙編3章の各floor(25×完成率/100)を合計する。現版00a5b084の集計カーネルを5条件で局所実行した。フルXP関数はゲーム状態・kind・クリア数・勉強力・お宝・コンボ・アイテムの取得helperを制御し、演算順を8条件で照合した。倍率・繰返し・割切れない値・0を含む。これは報酬付与やプレイヤーのセーブ状態の再現ではない。

ABI2へ別PODと関数を追加し、旧構造体は変更しない。入力の範囲はB/c非負、L=1..30、T=0..225、P=0..100、おかめ0/1。ネイティブ32bitの各乗算があふれる入力はエラー2とし、結果を部分更新しない。原本読込・お宝設定・クリア数保存をC++は所有しない。他番台や本編の経路はこの入口へ推測で混ぜない。

再現CLIはresearch/verify/experience.py。小さいfixtureのexperience-vectors.jsonをbridgeの1テストが5段階すべてと比較する。ServiceのlegendExperience配列入力へ接続し、ステージ詳細のXPが同じ関数を使う。

## 待機初期化と敵城行（0.1.8）

`stage::initialize`→`kbcs_core_stage_initialize`は、009eadc8の2区間を共用する。入力Startは全体間隔の下限/上限、0..差の抽選値、解決済みの敵城原ID（無効は0）。出力は全体待機と敵城行番号（なし−1）。行の待機はloaded列2を符号のままコピーし、生産数/撃破累計を0へする。元の状態は読まない。敵城指定があれば**前から最初の一致行**を返し、その行だけwait=1、spawned=1とする。通常tickの後ろ優先とは異なる。

呼出側が開始モードのフラグと敵城の存在を判定してcastle_rawを解決し、返された行の敵個体を1回生成する。原処理では生成helperの戻り値を検査せず行を消費するため、通常commitの「成功した場合だけ更新」をこの経路へ転用しない。C++が生成や演出を行う意味ではない。全体乱数は空の出現表でも1回消費する。全体間隔は読込後に×2しない。

stage_start.pyが009ee368..009ee520と009f0a60..009f0b58を局所実行する。vector領域は事前確保し、RNG、モード・敵城getter、個体生成を制御する。実命令の状態ゼロ化、負待機、空配列、重複時の先頭選択、非0モード、生成helperの失敗を6条件、実0番台全324面（敵城4面）で確認した。フレーム全体・城HP/攻撃倍率・個体初期化・セーブ状態の実行ではない。ABI2へ別PODと入口を追加し、旧型は維持した。入力不正時に状態を書きかけにしない。

## 開発素材（0.1.8）

007de628はDropItem列1..4を4係数、5..12を8回数、13をハズレ、14以降を素材重みとして読む。007df104の007df270..007df3a4は、float(count×multiplier)をdoubleへ拡張し0.5を加えて切り捨て、各回0..99抽選をハズレ値と比較する。ハズレ未満なら重み抽選の乱数は消費しない。当選時は重み合計を上限とする別乱数を使い、累積重みより小さい最初のスロットを1増やす。重み0の枠を詰め直さない。

`materials::plan`→`kbcs_core_material_plan`は回数と理論値を返す。m=miss/100、p_i=(1−m)×weight_i/Σweight、1回の当選p_i、1クリアに1個以上1−(1−p_i)^n、期待個数n×p_i、全素材なしm^n。独立一様抽選のモデルであり、ゲームの実乱数列・アカウントの結果を予測するものではない。通常ドロップの初回/取得済み分岐へは混ぜない。

`materials::pick`→`kbcs_core_material_pick`は同じ入力と明示した乱数から1回のスロットを選ぶ。ハズレ時はweight_rollなし（FFIでは−1）を要求する。乱数生成器・保存状態をC++は所有しない。固定16枠、重み非負、合計i32内、ハズレ0..100、係数/回数は有限非負、計算後抽選回数0..4096を受理する。抽選があるのに全重み0かつmiss<100は拒否する。エラー時に出力を部分更新しない。

materials.pyは現版の2段階抽選7条件、0.49/0.5付近の丸め、0重み、重み合計39と16枠SIMDの端、ハズレ100%を検査した。49マップ×4冠×8枠の回数1568条件も現版実命令へ通した。006f308cはGatyaitembuyの列6/7を格納した同版の表で全16素材IDを照合した。CSV/STLパーサー全体、素材の所持数加算、乱数生成器全体は未実装。

## 敵基礎値と通常報酬選択（0.1.9）

`enemy::stat`→`kbcs_core_enemy_stat`は現版00a9e9fc/00a9fb88の敵側・画面モード3の順序を共用する。出力3段階は、A=trunc((base×row_percent+50)/100)、B=trunc(A×crown_percent/100)、C=B+trunc(B×(crystal_max−crystal_treasure)/100)。敵城の**攻撃だけ**は冠を100として計算し、HPは通常どおり冠を適用する。合成倍率へまとめたり、冠の後を四捨五入したりしない。連続攻撃は敵原CSV3/55/56列の各段を別々に呼ぶ。味方の成長率・本能とは別入口。

row_percentはHPでは読込後9列、攻撃は11列が非0なら11、0なら9。原本の負値を保持した保存処理は変更せず、この非負計算APIは負倍率を拒否する。crystal_max/treasureは完成率そのものではなく、00a5b2d8/00a5b084に相当する集計済み効果量。通常エイリアンは効果16、スター1は18、スター2/3/4は22/23/24で、不足量を加算する。基礎値非負、行/冠0..1000000、最大効果0..10000、取得効果0..最大、城攻撃0/1。各出力がi32を超えればエラー2で出力を変更しない。

enemy_stats.pyは両関数の敵分岐全体を実行し、ゲーム取得・陣営フラグ・冠とクリスタル集計helperだけを制御した。48境界条件、全2924出現行×4冠=11696条件を対象とする重複除外8416プロフィールを照合した。通常/スター/神様、0、丸め境界、冠150/170%、明示攻撃倍率、敵城攻撃を含む。原本t_unitとSO SHAを確認した。対象0番台で合成倍率の四捨五入と差が出るプロフィールは212件（敵城の冠除外も含む）。個体生成・盾HP・本編の章倍率・戦闘フレーム全体は未実装。この追加関数を旧Webの全数値表示へ接続したという意味ではない。

`reward::legend_pick`→`kbcs_core_legend_reward_pick`は005d996cの通常報酬比較〜取得済み分岐を実装する。入力は候補数1..3、mode−1/1、先頭候補の取得済み0/1、レーダー0/1、比較値3枠0..100、候補ごとの明示乱数3枠0..99。入力3枠は未使用分も検査する。出力winnerは候補番号/なし−1、consumedは消費した比較乱数数、mark_acquiredは取得済み記録要求、radar_blockedはネイティブ補助フラグに対応する選択打切り。

各候補で乱数を消費し、roll<comparisonを先頭から評価する。レーダーでも乱数は消費し、比較値を100に置換する。mode1の先頭が取得済みなら、通常時は次へ進むがレーダー時は候補なしで打切り・radar_blocked=1。未取得の先頭が当選したmode1だけmark_acquired=1。所持数やセーブへは書き込まない。取得済みゲッターの冠別格納、アイテムの実付与、レーダーの返却/消費をこのフラグだけから推定しない。

rewards.pyはkind3・通常フラグ0・特殊報酬分類0を条件に、005dbfd4から005dd500/005dd52cへ至る命令を実行する。RNG・レーダー・取得済みgetter/setter・冠を制御し、getter/setterの引数も照合。境界48条件と実324面×取得済み2×レーダー2×乱数端2=2592条件。0番台の比較値は5列から、追加候補は9列以降の3列組、modeは8列で取得する。特殊分類1/2/3、mode2、−3/−4の重み、特殊フラグ、他番台、報酬付与関数006e34b0以降は対象外。対応範囲外のmodeを黙って通常扱いしない。

再実行：`research/verify/enemy_stats.py --assets <assets> --python-libs <libs> --publish`、`research/verify/rewards.py --python-libs <libs> --publish`。小さいfixtureを各1テストで比較し、大きい原本照合記録はresearch/.localへ置く。ABI2の既存型は維持し別POD/入口を追加。

1000番台の報酬/XPは[別の入口](event-rewards.md)を使う。種別1ではXPの×9とクリア数減衰を適用せず、mode−3/−4を通常比較へ渡さない。

0.1.12のスコア報酬はmode番号だけでなく原本15列の旗を見る。スコアの最高記録は付与試行後、mode−3の履歴は付与前に更新する。[契約・時計の単位・照合](stage-score.md)。

## 0.1.18: commitの再検査を原本へ合わせる

006ef2b0の最終候補は後方からwait<=0を選ぶ。有限回数・撃破・城条件はtickの待機更新に作用する条件であり、commitで再適用しない。commitは選択位置、行/全体待機、停止、容量、抽選範囲、整数上限を検査する。Rust PendingSpawnの消費所有権は維持する。

research/verify/stage_continuous.pyが同一状態で3tickを実行する。回数1/再待機0、城不成立/列12非0、個体枠なしの3ケース。成功では生成回数1→2→3、各tickのRNG boundはレイヤー10→全体1→行1。空きなしは生成0、RNG不変。原本009f1e64は枠探索・レイヤー抽選まで実行し、00aa0aa4以降の個体構築だけ成功へ制御する。全戦闘/全個体構築の照合ではない。小さい追跡fixtureはtests/stage-continuous-vectors.json。
