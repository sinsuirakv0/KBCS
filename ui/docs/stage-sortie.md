# 既存ステージの出撃準備（0.1.28）

ステージPlayの「既存マップから」→既存stage-searchのplay=1モード→stage-sortie。通常のDB検索・詳細画面は維持する。playフラグはnative-stateがURLに保持し、検索条件は従来の検索UIを流用する。普通の検索へ戻るとplayを除去する。

## UIと保存

左は選択マップ内のステージ一覧。中央はステージ名・冠・折りたたんだ敵一覧・使用編成・自城体力・6アイテム・出撃。右サイドバーは詳細なステージ情報・有効な出撃制限・特殊条件・固定編成・背景と城・BGM試聴。長い報酬表・出現条件表はDB詳細に残す。抽選ステージは原本候補を明示選択するまで出撃を無効にする。

GET /api/formations?list=1はID・revision・名前だけを返す。選択した1件のprofileを取得し、編集はそのIDの編成画面を開く。battleFormationは設定をコピーしてresolveFormationMemberを通し、Lv不足の第四形態や超本能を実効値へ変換する。出撃前に保存revisionを再確認し、変更されていれば再確認を求める。出撃操作で編成DB・公式DB・本家の所持品を変更しない。

城砲にはdevelopmentLevel（城開発Lv1〜30）を追加。編成単位で保存し、古いファイルの欠測は30として扱う。施設の「お城体力Lv20+10」とは別。castleHealthInputは施設合計・日本編group4と未来編group2の章別お宝・先頭5枠の城体力コンボを組み、POST /api/battle-support→Rust bridge→C++へ渡す。画面の値は編成の設定値による見積もりであり、特殊ステージの施設上書き処理はまだ接続していない。

アイテム0〜5はスピードアップ・レーダー・ネコボン・ニャンピュータ・おかめ・スニャイパー。速度は2/3の選択で、OFF時のsnapshotは1。選択はsessionStorageだけへ保存する。城体力・スニャイパー・速度の原本と範囲は[native設計](../../native/kbcs-core/docs/battle-support.md)。

## 暗転と初期盤面

出撃時にステージ・冠・編成保存版・実効キャラ設定・アイテム・明示シード・制限一覧をコピーする。battle-support.prepareBattleAssetsは敵/味方のmanifestを最大4並列で読み、身体・魂・背景/城のテクスチャをパスで重複除去してデコードする。ロード中は黒画面と進捗、取消を表示する。欠測・失敗時は初期化に成功したように扱わず準備画面へ戻す。

背景・城の描画はnative-mediaから公開したloadStageScene/paintStageSceneを共用し、C++描画命令をGPUへ送る。読み込みが終わって初期盤面を描いてから暗転を外す。途中で取り消したロードの結果は表示しない。

今回は出撃準備・素材ロード・C++による0F初期盤面まで。継続的な戦闘、敵生成・キャラ出撃・攻撃・移動・スニャイパー弾の時計、ニャンピュータ等のアイテム効果、固定編成や可変生産条件などの適用、BGM再生は未接続。0Fと戦闘進行未実装を画面に明記し、経過時計や勝敗を仮生成しない。原本由来の制限・ステージ設定はsnapshotに保持し、後続の戦闘入口で解決する。背景描画と戦闘RNGは独立している。

次のランタイム実装はsnapshotを直接の戦闘入力にせず、ステージ固有の上書き・編成制限・初期出現・資金等を検証してからC++状態を作る。stage tick/commitや弾到達のRNG順は既存の監査契約を維持する。


0.1.27では最後に一致した出撃制限行を表示し、レア度・枠・コスト・キャラ群・レア度別編成数をstageDeployment→/api/deployment→C++で判定する。出撃不可のキャラを保存編成から消さず、slots[].reasons/formationReasons/costをsnapshotへ残す。戦闘の出撃入口はこの禁止状態を確認する必要があり、0F盤面表示だけで戦闘中の出撃処理を実装した意味ではない。編成編集へのリンクには同じmap/stage/crownを渡し、編成上でも原本の編成不可画像を表示する。動的な同時出撃数や資金を静的な編成検査と混同しない。

表示名はformationDisplayNameでslotName優先、旧nameは互換用のフォールバック。「新しい編成/名前」を連結しない。編集時の名前は双方を同期し、pageshow/focus/storage通知で一覧と選択中の保存版を更新する。城体力の折りたたみ内訳はC++の施設・城開発・お宝・コンボ加算で、通常最大は78000+116000+42000=236000。

0.1.28ではstageRulesHtmlのselectedLimitsへ最後に一致した行のみを渡す。DB詳細の従来表示は既定値で維持する。stageMediaHtml/initializeStageMediaを共有し、ステージ・冠・抽選パターン変更時に音声とプレビューを解除して再接続する。初期盤面へ進む際も試聴を止める。sidebarのDOMはworkspaceが移動するだけで複製しない。キャラ共用SVGの寸法はnative.cssへ集約する。


## 0.1.29: 戦闘画面

出撃後はworkspaceのステージ一覧・情報を非表示にし、両ペインを一時的に閉じる。準備へ戻ると直前のペイン状態へ戻す。戦闘中のサイドバー内容は後続のUI整備まで空けておく。ui/battle-screen.jsはHUDのアトラス転送とポインター標本化、native/battle_screen.cppは経済・暗転・ページ・入力待ちを担当する。キャラ出撃は解放後5回の入力更新を経た要求までで、生成・残高消費・再生産時計の確定は未接続。原本と照合範囲は[native設計](../../native/kbcs-core/docs/battle-screen.md)。

全対象のbody/soul、背景/城、HUD、編成アイコンのデコード完了後、C++の12F全面暗転から13〜23Fの退出へ進む。30更新の蓄積器はHTTP待ち中も未処理時間を保持し、並行する状態更新を出さない。画面が隠れると停止要求を送り、停止中に経過時間を蓄積しない。Canvasの表示矩形は3:2を維持し、レターボックスをヒット座標へ含めない。

一時停止は再開・1/2段・ページ選択・準備へ戻る操作を用意したKBCS側メニュー。ネイティブの全オプションウィンドウ移植とは区別する。特殊スロットの精霊/召喚/追加生産装飾、再生産の実確定、全特殊ステージの初期化、カメラ操作・背景の連続演出、戦闘BGMは残る。GUI上で敵を自動生成しない。


## 0.1.30: 戦闘HUDの更新

上の0.1.28/29の実装範囲から更新。battle-screen.jsのリサイズは画面高640・可変幅でC++ stage-sceneを1/2段分取得し、別Canvasへ描画後に交換する。C++の2段カメラ-51pxと下地680までの命令を使い、固定3:2と背景の単純移動を廃止。古いDBプレビューの既定値は維持する。画像読み込みは暗転中、表示確認はユーザー担当。

空き枠uni、1段の縦スワイプ/ホイール、金額の短い白点滅、黄色で固定の財布MAXとLEVEL8、砲準備完了の2相を原本へ接続。3倍対応の速度はOFF/2/3、通常はOFF/2。アイテムの説明と押下拡縮を追加。battle-screen.cppが矩形・状態を返し、JSは画像転送と入力標本化を担当する。

停止メニューはimg100の戦闘専用配置へ変更。BGM4段階はstage-audioへ接続、SEは状態のみ、PCの振動は非対応表示。ヘルプはユーザー指定URL。キャラ確認は2段へ切替え、選択枠・名前・説明を表示して終了時に元の段数へ戻す。特性アイコン行と離脱確認/返還条件は未接続。現段階の離脱は生成前の出撃準備へ戻るだけ。敵/味方の生成や攻撃を開始した扱いにしない。原本・座標・局所照合は[native設計](../../native/kbcs-core/docs/battle-screen.md)。


## 0.1.31: 背景時計・カメラ・BGM

battle-screenの開始時1枚のキャッシュを廃止し、C++状態のframeが変わったときscene API→共用C++描画/演出→WebGLへ接続。1/2/3倍は論理時計、停止中は同じframeを保持する。カメラや段数変更だけなら同じframeで描き直す。背景用Canvas2枚を交換して使い回し、HTTP/描画は1要求ずつ処理する。初期のscene.texturesに含まれる演出画像は従来どおり暗転中にデコードする。

盤面の上部HUDとスロットを除いた領域でドラッグ移動、ホイール/ピンチで拡縮。sceneGestureViewをDB試写と共用し、viewport_widthに合わせて入力点の世界位置を保つ。上限はbattle_rowsありで1倍（005cb0e0の10000上限）、DB試写は従来の2倍。小さい城以外の個別ズーム上限やAndroid慣性入力の全再現ではない。入力点の絞込みはPCの操作アダプタであり、Android全入力関数の移植とは区別する。

BGMは暗転中にAPIからBlobへ取得し、読込後に開始。曲ごとの実MIMEで再生し、終了/取消でBlob URLを解放する。新しいassets buildIdでも、戦闘UI画像とimgcutの全SHAがDBのasset_referenceに一致すれば同じUIを使える。ゲーム版だけで未知の差し替えを許可しない。画面検査はユーザー担当。
