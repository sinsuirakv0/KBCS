# 15.7.2と15.7.4の関数照合

## 比較対象

両版のJP / arm64-v8a / `libnative-lib.so`。Ghidra 12.1.2の完了チェックポイントを復元し、公開manifestのSQLite SHA-256と一致することを確認した。内部25,233関数ずつを使用した。

| 版 | 解析ID | SO SHA-256 |
| --- | --- | --- |
| 15.7.2 | `5ed057380ac853a2` | `6122e24879d58db6b0beceb43e2a6ee62d008a586fc03b7cb7726214bc86f3ea` |
| 15.7.4 | `6cf79e30b2bdfc73` | `669438f86b41c10c7a387b96eb1ab5ca82a350bacc89ec06c05f699ec3727590` |

## 照合方法

1. `llvm-readelf --dyn-syms --wide` から両版にある定義済み関数シンボルを取得する。ELFのロード基準とGhidraのイメージベースを使ってアドレスを変換し、SQLiteの関数に結びつく一対一の組を基準にする。
2. 疑似コードの本体を字句に分ける。宣言、空白、コメントと、Ghidraが生成したアドレス付き識別子の数字だけを比較から外す。同じ識別子の再出現は同じ番号で表す。数値定数、文字列、演算子を残し、両版で一意な本体指紋を候補にする。確度lowの疑似コードは指紋候補から外す。
3. 64字句以上の指紋候補を、同じ方向の対応済み呼び出し辺、または両版でそれぞれ5関数以下にしか出ない共通文字列で補強する。
4. 指紋で照合できなかった関数は、異なる対応済み関数2件以上との呼び出し方向の集合が両版で一意に一致し、短い方のサイズが長い方の75%以上のものを別枠で拾う。
5. ELFで対応する関数の一部を、シンボル名のSHA-256で固定抽出して評価用に取り分ける。その組を呼び出し照合の基準から外し、各ルールの正解と誤対応を測る。

## アドレス移動の実測

両版に共通するELF関数シンボル名は4,978件。両方のGhidra関数索引に結びつく一対一の対応は4,592組だった。内訳は `+0x10c` が3,485組、`+0x108` が4組、同アドレスが1,103組。

検証用1,477組のアドレスを伏せ、旧アドレスを挟む既知シンボル2件の移動量が同じ場合だけ、その移動量で新版の候補アドレスを探した。候補が出た1,475組はすべてシンボル由来の正解と一致し、残り2組は候補を出さなかった。この2版の範囲では、両側の移動量を候補探索の範囲に使える。他の版や名前なし関数にも同じ精度が出るかは別途検証する。

ELFシンボルで対応が確定していない指紋候補では、前後の移動量と比較できた64字句以上の1,429組はすべて予想アドレスと一致した。64字句未満では421組が一致し、34組が矛盾した。短い本体の一致は単独採用を避け、追加の根拠を確認する。

## 実際の差分から得た手がかり

- アドレスが移動した名前なし関数の例は `009b79e8` → `009b79f4`。関数サイズ676バイト、疑似コード指紋と希少な関連文字列1件が一致した。
- 既存の戦闘検証で扱う `006d6d04`、`006e4aec`、`006e79bc` は両版で同じ位置とサイズ。補助比較では空行・インデントと既知のアドレス付きラベルを正規化し、3,911行中3,908行、854行中853行、763行中762行が一致した。この3組は最初の指紋照合から漏れた。
- 3関数すべてに `thunk_FUN_00a94484` → `thunk_FUN_00a944c8` の差があった。SQLite上の呼び出し先は両版とも428バイトで、どちらにも `0081f580` への呼び出し辺がある。`006d6d04` の残り2行は型情報への `PTR__ZTV...` ラベルのアドレス差だった。
- `MyActivity_onIapList` の同名関数では `s_price_amount_micros_...` と `PTR__ZN...` の末尾アドレスが変わった。次の指紋実験ではGhidraの文字列ラベル、`thunk_FUN_...`、C++のシンボルを含むポインタラベルを正規化対象に加え、文字列そのもの、型名、定数、呼び出し先の対応を残す。これらの観察で分かるのは当該行の差で、動作の同一性は命令や参照先を含めて確認する。
