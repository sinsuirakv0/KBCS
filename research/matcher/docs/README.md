# 版をまたぐ関数探索

既存のGhidraキャッシュを読み取り専用で使い、版間の関数対応と未確定候補をSQLiteへ保存する。Python 3.11以上の標準ライブラリだけで動く。Ghidraの再起動、再デコンパイル、外部API、LLMへの疑似コード一括送信は不要。

全関数を台帳に載せることと、全対応を確定できることは区別する。削除・追加、インライン化、関数分割・統合、同一コードの折り畳みがあると1対1の対応が存在しない場合もある。この版は1対1の推定対応を作り、判断できない関数は残す。未確定を削除・追加と断定しない。

[15.7.2 → 15.7.4の実測結果](results-15.7.2-15.7.4.md)に対応数、残った課題、速度・容量、今回のDBパスを記録した。

## 実行

リポジトリのルートで実行する。`--old-cache` と `--new-cache` は `cache.sqlite` と `code/` を含む完成済みキャッシュを指定する。SOは任意だが、指定すると名前付きの基準を増やせる。SHA-256がキャッシュと一致するARM64 ELFに限る。

```powershell
$env:PYTHONPATH = (Resolve-Path research).Path
python -m cli.match build `
  --old-cache research/.local/comparison-inputs/15.7.2-5ed057380ac853a2 `
  --new-cache research/.local/comparison-inputs/15.7.4-6cf79e30b2bdfc73 `
  --old-binary research/.local/apk/150702/libraries/arm64-v8a/libnative-lib.so `
  --new-binary research/.local/apk/150704/libraries/arm64-v8a/libnative-lib.so `
  --validate
```

完了時に表示される `matches.sqlite` を指定して検索する。アドレスはGhidraの値。版・ABI・SHAは `stats` で必ず確認する。

```powershell
$db = 'research/.local/matching/<表示されたrun_key>/matches.sqlite'
python -m cli.match stats --db $db
python -m cli.match find appUpdateDraw --db $db
python -m cli.match show 006d6d04 --db $db
python -m cli.match show 006d6d04 --side new --db $db
python -m cli.match find --status review --limit 5 --db $db
python -m cli.match find --status unresolved --side new --db $db
python -m cli.match gaps --status changed_count --db $db
```

`show` は対応先、両版の資料パス、採用理由、対応済みの呼出関係や文字列の例、前後の基準、競合候補との点差を返す。未確定の場合は上位候補を返す。`find` は名前・アドレスと状態を検索し、`--offset` でページを進める。未確定の理由も `review_reason` に保存する。根拠不足、競合、低確度の復元、候補なし、反復上限等を区別する。出力は既定5件、最大20件。疑似コード自体は既存の `cli/cache.py` または表示された関数資料で読む。

## 根拠と採用

1. SOの動的シンボルと外部関数名を使い、両側で一意な名前を基準にする。名前の別名が矛盾する場合は自動採用しない。
2. 関数本体をトークン化して指紋を作る。コメント、空白、関数ヘッダを除き、`FUN`、`thunk_FUN`、`DAT`、`PTR`、文字列・型情報等のラベル末尾のアドレスを正規化する。同じラベルの繰り返し関係を保持し、数値、文字列リテラル、演算子、名前付きシンボルを残す。
3. 変数名の差を許す別の指紋と、4トークンの並びの小さな要約も作る。後者の一致度だけでは採用しない。
4. 対応済み関数の隣接区間を調べる。区間の関数数が等しい場合は同じ順位を候補にする。両端の移動量が同じ場合は同じ移動量のアドレスも候補にする。関数数が異なる区間は比例位置の近傍だけを候補として調べる。基準が逆転・交差した区間では順序を証拠にしない。
5. 他関数の入口への末尾ジャンプも呼出関係へ加える。共有データは、対応済みの2関数以上からの参照者・READ/WRITE等の種類が両側で一意に一致する場合に対応候補を作る。同じ参照者集合を持つ複数フィールドは曖昧なので使わない。これに加え、対応済みの呼出元・呼出先、両版で利用箇所が少ない文字列、関数サイズ、エクスポートされた範囲の機械語バイト列でも絞る。間接呼出しはGhidra索引に記録された範囲だけを使う。
6. ARM64で8〜128バイトの短い関数は、Ghidraの本体サイズが入口から最初のRETまでの一本道と一致し、途中に分岐・例外・システム命令がない場合だけ機械語全体を比較する。本文と機械語が一致し、少なくとも片方の指紋が両側で一意で、順序・移動量も一致する場合は追加の採用候補にする。全体で同型が複数ある場合でも、前後の基準間が両側とも最大4関数で、本文と機械語がその区間内ではそれぞれ一意なら局所対応を採用できる。
7. 本文に変更がある場合も、トークン要約の一致度0.85以上・サイズ比0.75以上・順序・移動量・3本以上の対応済み呼出関係が揃えば採用候補にする。順序によらない場合は一致度0.92以上、5本以上の呼出関係と希少文字列を要求する。
8. 複数の根拠を満たし、旧→新と新→旧の両方で最良で、次点との差が両方向とも8点以上の候補を採用する。短い同型関数は順序・移動量に呼出関係または共有データの裏付けを要求する。本文の指紋と対応済みの呼出近傍の組が両側で一意な場合も採用候補にする。低確度の復元コードはコード根拠で自動採用しない。
9. 局所区間の一意性に依存した `leaf_bytes_and_local_order` の対応は、以降の順序・呼出・データ参照の基準にはしない。他の採用済みの対応を次ラウンドの基準に使う。最大12ラウンドで追加を終え、最終候補を再計算する。総当たりの全組合せや無限反復は行わない。

スコアは候補の順位付けに使う手作業の重みであり、正答確率ではない。複数の根拠も完全に独立ではない。採用は同じ由来の関数という推定であり、同じ挙動であることの証明ではない。前後の順序は有力な補助だが、ビルド設定や最適化が変わると崩れる。

`text_equal` は疑似コード全体のハッシュ一致、`normalized_equal` は正規化した本体の一致、`different` は本文が異なる対応、`unavailable` は比較できる本文なし、`external` は外部関数。数値や文字列が変われば本文差として残る。

## 検証と人の修正

`--validate` は名前で対応が分かる内部関数の約1/3を固定的に選び、その名前による初期対応を隠して全工程を実行する。正答、誤答、保留を分けて報告する。正答があり誤答0なら `quality_gate=passed_named_holdout` となる。ただし名前が残る関数の検証であり、匿名関数全体の精度や100%正答は保証しない。検証結果から自動的に閾値を変更しない。検証失敗時も診断資料は保存し、コマンドは非0で終了する。

出力先の `review-template.json` をコピーし、`decisions` に判定を追加して `--decisions <ファイル>` で再実行する。

```json
{"old":"006d6d04","new":"006d6d04","action":"accept","note":"両版の分岐と呼出先を確認した"}
```

`action` は `accept` または `reject`。理由は必須。テンプレート内の `sources` は両版の索引SHA-256なので残す。異なる索引への流用、多対1、採用・却下の矛盾は停止する。シンボル基準を覆す場合はその元の組を明示的に却下する。手動判断はホールドアウト検証に混ぜない。指定が変わると別の実行IDに保存し、元の結果を残す。

## 保存と関数の関係

| ファイル・関数 | 役割・接続 |
|---|---|
| `features.signature` | 本文から2種類の指紋と候補探索用の要約を作る |
| `features.read_elf` | ELF64 ARM64の動的シンボル、エクスポート範囲のバイト指紋を読む |
| `features.load` | 原索引・参照を読み、指紋SQLiteを再利用して `engine.match` へ渡す |
| `relations.enrich` | 原索引から末尾ジャンプと共有データへの参照を追加する |
| `relations.leaf_bytes` / `straight_leaf` | 短い一本道の関数だけ本体範囲を確認し、完全一致する機械語を補助根拠にする |
| `relations.data_pairs` / `context_pairs` | 複数の基準で共有データを照合し、コードと呼出近傍の一意性を調べる |
| `engine.unique_pairs` / `symbol_pairs` | 一意性と別名の矛盾を確認する |
| `engine.order_candidates` | 前後の基準・順序・移動量から局所候補を作る |
| `engine.match` | 候補集合、根拠、両方向順位を計算し、対応を反復的に増やす |
| `report.validate` | 名前付きの正解を隠して `match` を再実行する |
| `report.build` | 指紋取得→照合→検証→DB・レポートの保存を制御する |
| `report.save_database` | 全関数の状態、対応、候補、区間、再現情報を保存する |
| `cli.match.query` | SQLiteを読取専用で検索し、必要な少数だけ返す |

生成物は `research/.local/matching/` 内に保存する。

- `features/*.sqlite` は索引SHAと抽出実装SHAごとの指紋。ファイルサイズ・更新時刻が同じ疑似コードを再利用する。初回は本文を読むが、照合ルールだけを変えても本文を読み直さない。256件ごとに保存し、中断後に再開できる。
- `<run_key>/matches.sqlite` は主成果物。`functions` に両版の全関数、`matches` に1対1の採用、`candidates` に旧関数ごと最大8件、`gaps` に区間、`metadata` に版・SHA・実装・判断・検証・時間を保存する。
- `matches.tsv`、`candidates.tsv`、`functions.tsv`、`gaps.tsv` は他のローカルツールから読める形式。`summary.json` と `report.md` は実測結果、`review-template.json` は人の判断用。

原索引の前後ハッシュとSOのSHAを検査する。OSロックで同一指紋・同一出力への同時書込を防ぐ。DBは一時ファイルで完成・整合性検査後に置き換える。同一出力先に異なる実行を上書きしない。補助TSV等の保存中に中断した場合は同じコマンドで再作成できる。原キャッシュ・Ghidraプロジェクト・公開済み資料は変更しない。

## 現在の範囲と拡張

CFGやP-codeは現在の索引にないため、この実装では抽出済みであるかのように扱わない。一般の匿名関数は本体が不連続である可能性があるので、単純なアドレス＋サイズで機械語全体を切り出さない。前述の一本道を確認できる短い関数だけを例外にする。

今後は未確定を中心に、本体範囲、基本ブロック、P-code、呼出先順序をGhidra側で局所抽出して追加できる。インライン化・分割・統合は別の多対多の関係として保持し、現在の1対1表へ無理に押し込まない。十分に検証した対応を公開する段階で、既存関数資料へ相互リンクを追加できる。

```powershell
python -m unittest matcher.test_matching
```
